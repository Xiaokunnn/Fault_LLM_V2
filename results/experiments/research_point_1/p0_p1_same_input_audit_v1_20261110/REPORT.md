# P0 / P1 同输入回放与根因复核

日期：2026-11-10。对象为研究点一候选验证问题，不改变研究点三LEC或任何冻结教师。

## 结论

**当前不宜将C类验证损失发展为独立学术创新；B类的代表性反向因果也尚未构成需要新算法的证据。**

这不是因为五项C已经全部修好。实际情况是：一项明确解决，一项部分解决，一项仍被工程接口问题阻断；另两项原来的“完整正确但误拒”标签需要收窄或撤回。剩下两项引句问题是同一个规则链接口回归，不是两个独立的语义难题。

“超压导致叶轮损坏”的反转已经存在于保存的模型原始解析JSON；提示中的Schema方向明确，后处理没有制造它。最新版已有类型方向归一化函数已纠正这一例。但仅凭原始反向输出，不能区分模型真正误解因果与输出时的角色/序列化错误，不能直接推断内部认知原因。

本轮还发现：引句与类型通过不保证语义正确。C所在三页的新流程新增放行18条，经本次非盲AI源文审计，13条支持、2条不合格、3条待定。该结果只描述这些新增放行项，不是全流程准确率，更不是专家真值。

### 两个仍被拒绝的正确C候选，为什么在新版也失败

`MP021:p0015:H29:002`与`MP021:p0020:H29:006`均出现同一实际轨迹：

### “超压→叶轮损坏”能确定什么

原PDF物理第3页右栏PRESSURE段及实际请求都提供了超最大运行压差导致叶轮损坏的内容。原始响应还引用了这一正确句子，但角色字段是：

`head = damage to the Impeller, head_type = FaultMode`

`relation = causes`

`tail = operate the pump above the maximum differential pressure ..., tail_type = OperatingCondition`

原提示的`causes`明确为原因/机制/条件/故障指向机制/故障/症状/风险，且`inverse_storage_allowed=false`。它不允许把OperatingCondition放在结果端。因此，没有发现这一例中Schema定义或方向相互矛盾的证据。

`parse_response`直接`json.loads(choice['message']['content'])`，旧对照分支复制原载荷；同输入回放也证明旧后处理没有把正确边翻错。最新版首先调用`normalize_relation_direction`，产生`reoriented_cause_to_effect`，随后布局绑定通过。该函数在更早的仓库提交`fdd2c417`已经存在，并非本轮新写算法。

准确归因是：**错误最早可定位在生成端的角色输出；旧对照链还缺少既有归一化接入。**它不等于已经证实模型不懂超压损坏机理。读懂句子但序列化颠倒、受输出格式影响等替代解释，在本轮没有被受控重测排除。

### 什么仍有待验证

本轮能排除“错误是后处理翻出来的”，并证明这条简单反向可由现有通用类型归一化修好；但未重新运行同一LLM，未比较显式方向模板、类型约束/指针输出等通用方法的多次稳定性，也未证明新算法收益。

对MP006 p6的三角色问题，可以保留为后续困难样本；在没有与通用结构化输出、条件—对象—动作分离等简单基线比较之前，不能将它升级为独立算法的充分动机。菜单方法端点问题也应先排除“输入接口根本不能表示正确方法”的情况。

## 四、研究与工程边界

P0：不建议继续把本轮C样本作为独立创新点。明确解决的是已有原生布局绑定；残留的重复引句回归是工程契约问题，另有维护/运行Schema边界及OR逻辑表示问题。代码定位、定性诊断和同输入反例可作为系统验证材料，但不等于新算法。

P1：不建议以“超压反向”支撑新语义算法。现有类型归一化已经解决；复杂角色绑定只能列为待验证问题，尚未达到“现有通用方法无法稳定解决”的证据要求。

如果下一步做工程修复，先保持多片段证据证明在layout与batch之间一致传播，加入否定状态及动作目标的防错回归，并明确替代动作与运行/维护边界。**本轮只定位，没有修改生产规则、Schema、原候选、论文或图谱。**修复后再以同一输入重测新增正确放行与新增错误放行，不能只报告通过数增加。
