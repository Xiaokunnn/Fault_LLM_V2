# 研究点三优化与方向调整报告：从“端到端轻量证据控制器”转向“证据核验蒸馏与选择性边缘推理”

## 总体判断

结合你截至 **2026 年 9 月 18 日** 的实验结果，以及我对仓库中 RP3 最新实验报告、范围复核、基线与 TODO、三研究点规划和近期提交的检查，我的判断比较明确：

> **研究点三不建议继续沿当前“多头 LEC 端到端学习证据排序 + 支持判别 + 数量预测 + 路由”的路线继续堆损失、编码器和结构。**
>
> 但也**不建议放弃“知识蒸馏与边缘部署”这个研究点**。
>
> 最合适的调整是把蒸馏目标收窄，从“蒸馏整个 GraphRAG/教师决策策略”改成：
>
> **“蒸馏最昂贵、最适合学习的证据核验能力，并通过风险约束的选择性执行机制决定本地回答、教师回退或拒答。”**

因此，我建议研究点三正式改成：

> **面向船舶机舱泵系故障辅助诊断的轻量证据核验蒸馏与风险约束边缘推理方法**

或者更偏论文式：

> **基于证据核验蒸馏与选择性回退的船舶泵系边缘辅助诊断方法**

整个论文的三点主线仍然完整：

\[
\boxed{
\text{RP1：可靠知识怎么构建}
\rightarrow
\text{RP2：可靠证据怎么选择}
\rightarrow
\text{RP3：可靠证据怎么低成本使用}
}
\]

而不是现在 RP3 试图重新学习 RP2 已经解决的问题。

### 对当前几个选择的判断

| 方案 | 建议 | 原因 |
|---|---|---|
| 继续调 C0/W1/J1/G1 | **停止** | 已出现明确的精度—拒绝率冲突 |
| 换更强语义编码器 | **停止** | E1 已经证明成本显著增加但质量下降 |
| 继续设计新的联合损失 | **不建议** | 根本问题是独立场景太少和任务过载，而非缺一个 loss |
| 增加大量同场景数据增强 | **只能辅助** | 165 条不能改变只有少数独立场景的事实 |
| 继续做 `<50M` 端到端 evidence controller | **不作为主线** | 当前数据条件难支撑多任务联合学习 |

## 当前实验真正暴露的不是“模型不够强”，而是任务定义过重

你现在最重要的事情不是找新的网络，而是正确解释为什么目前结果会这样。

### 一个不到五千万参数的模型被要求同时学了太多事情

当前 LEC 实际上同时承担：

\[
x \rightarrow
\begin{cases}
\text{候选证据排序}\\
\text{证据指针选择}\\
\text{直接支持判定}\\
\text{字段数量预测}\\
\text{欠填判断}\\
\text{本地/教师/拒答路由}
\end{cases}
\]

而真正独立的数据基础只有：

> 32 条原始训练、8 条验证，对应 8 个训练场景和 2 个验证场景。

增强至 165 条并没有增加真正独立的诊断场景。

因此，这不是典型的“小模型容量不够”，而更像：

> **学习问题的自由度远大于数据能够支撑的自由度。**

你的实验恰恰支持这个判断。

C0 达到当前最好 Pointer F1 0.3472，但出现误填；W1/J1 用困难负例和联合契约把误填压至 0，却把 Pointer F1 打到 0.075，大量正常非空任务被拒绝；G1 加正支持保护只恢复到 0.1972；S0/S1 的集合上下文没有超过 C0；E1 引入约 2541 万参数的语义编码器后，F1 只有 0.2792，而且一个种子误填增加到 4/12。

这说明当前真正的矛盾是：

\[
\boxed{
\text{减少误填}
\Longleftrightarrow
\text{提高拒绝}
\Longleftrightarrow
\text{降低非空召回}
}
\]

继续增加 hard negative 很容易让模型学会一个最安全的策略：

> “不确定就什么都不给。”

而这正是 J1/W1 已经表现出的现象。

### E1 是一个非常有价值的负结果

E1 不是“实验失败，因此没用”。

恰恰相反，它帮你排除了一个很重要的假设：

> **问题并不是因为 C0 没有足够强的语义表示。**

E1：

- 参数量约 25.41M；
- 仍满足 `<50M`；
- 同后端 CPU 组件延迟约 82.3 ms；
- C0 只有约 4.8 ms；
- F1 反而从 0.3472 降至 0.2792；
- 正确非空提案没有增加。

也就是局部推理成本约增加到原来的十几倍，却没有形成质量收益。

硕士论文完全可以把这解释为：

> 对冻结候选证据集合而言，进一步提高文本编码容量并不能解决稀疏监督条件下的集合级决策问题，因此研究重点由语义编码能力提升转向任务分解与选择性推理。

这个解释比“再换一个 encoder”有价值。

### 当前验证集已经不能继续承担模型选择与部署认证两个职责

MP008 已经被反复用于：

- 模型选择；
- 阈值拟合；
- 多轮结构调整；
- 支持门控检查；
- 路由校准。

因此它现在应该明确定位成：

> **development set**

而不是再称为真正独立的部署验证集。

更关键的是，MP008 只有 3 个教师非空任务，而你的规则又要求至少接受 5 个非空答案。这不是“模型还没训练好”，而是一个**数学上不可能满足的验证设计**。

甚至即使你把门槛改成 5，也不能称为“10% 错误率的可靠认证”。

举个非常直观的例子。

假设接受的 \(n\) 个独立非空任务中 **一个错误都没出现**。在简单 Bernoulli 假设下，单侧 95% 错误率上界为：

\[
p_{upper}=1-0.05^{1/n}
\]

如果：

\[
n=5
\]

即使 5 个全对，上界仍约为：

\[
45.1\%
\]

只有：

\[
n\ge29
\]

且 29 个全部正确时，95% 单侧上界才首次下降到约 10% 以下。

而你现在只有 3 个非空任务，所以不论模型多优秀，都无法形成有说服力的“≤10% 部署风险”结论。

Conformal Risk Control 这类方法确实可以给风险控制提供理论框架，它把 conformal prediction 扩展到了更一般的单调损失风险控制；但它依然依赖足够且适当的校准样本，算法不能凭空解决“只有三个独立非空案例”的信息不足问题。citeturn6academia50

因此：

> **RP3 的第一优先级不是换模型，是重新定义学习任务和验证协议。**

## 推荐的新研究点：只蒸馏“证据核验”，不要蒸馏整个证据选择策略

这是我最推荐的调整。

RP2 已经负责：

\[
q
\rightarrow
\text{候选证据检索}
\rightarrow
\text{路径打分}
\rightarrow
\text{排序}
\rightarrow
C=\{e_1,\ldots,e_m\}
\]

RP3 不应该再训练一个小模型重新预测：

> 哪几条证据应该排第几、这个字段应该放几条、最后走哪条路线……

这些内容大量重复 RP2。

新的 RP3 只回答一个核心问题：

> **对于 RP2 已经检索出来的候选证据 \(e_i\)，它是否足以直接支持当前请求字段？**

也就是把训练单位从：

\[
\text{整个诊断场景}
\]

改成：

\[
(q,\;role,\;e_i)\rightarrow
\{\text{支持},\text{不支持}\}
\]

必要时可以用三分类：

\[
\{\text{support},\text{unsupported},\text{uncertain}\}
\]

我更建议第一版先用二分类概率 + uncertainty，而不是直接三分类。

### 新架构应该非常简单

整个系统改成：

```text
结构化故障查询
      ↓
RP2 冻结检索器
      ↓
Top-N 候选证据
      ↓
轻量证据核验器
      ↓
每条候选：
p_support
      ↓
确定性证据契约
      ↓
┌─────────────┬──────────────┬────────────┐
│ 高置信支持    │ 不确定/冲突    │ 无有效证据   │
↓             ↓              ↓
本地回答       7B教师回退       拒答/人工复核
```

这里发生了一个非常重要的简化。

### 删除 Pointer Head

不再要求学生：

> 从所有候选中重新预测证据位置。

因为 RP2 已经有排序。

学生只对：

```text
rank 1
rank 2
rank 3
...
```

逐一核验。

最终顺序直接沿用 RP2 排序。

### 删除 Count Head

不再让学生预测：

> 这个字段应该填 0/1/2/3 条。

改为规则：

```text
从 RP2 排序后的候选中，
依次保留 p_support ≥ τ 的证据，
最多 K 条。
```

如果只有一条满足，就填一条。

没有满足就欠填。

因此“欠填”不再是一个要学习的标签，而是：

\[
|\hat S| < K_{required}
\]

的确定性结果。

### 删除 Requested Field Prediction

请求字段本来就在结构化 query 里，例如：

```json
{
  "requested_fields": [
    "cause",
    "inspection",
    "maintenance"
  ]
}
```

模型没有必要重新猜：

> 用户现在是不是需要 maintenance？

它是已知输入。

这样天然消灭“非请求字段误填”这一类错误。

### 第一版也删除独立的 Route Head

当前 route head 要同时学习：

```text
local
teacher
reject
```

这又增加一个学习任务。

第一版建议把 route 改成**风险规则的确定性结果**：

```text
所有必需字段都有高置信支持
+ 无冲突
+ 非 OOD
→ LOCAL

至少一个必要字段不确定
或证据置信度落在灰区
→ TEACHER

无支持证据
或明确超出知识范围
→ ABSTAIN
```

后面如果数据量足够，再研究学习型 router。

这种设计与 learning-to-defer 的基本思想完全一致：模型并不需要在所有样本上自行作出最终决策，而是在自身可靠时预测，困难样本交给专家。citeturn6search2 RouteLLM
